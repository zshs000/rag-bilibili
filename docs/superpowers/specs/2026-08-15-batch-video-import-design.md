# 批量视频异步导入设计

## 目标

在保留现有单视频导入入口的基础上，支持用户一次粘贴多行 B 站视频链接或 BV 号，并异步查看整批及单项进度。批量导入复用现有单视频导入能力，不引入消息队列。

## 范围

- 单批最多接收 50 个视频，后台固定并发数为 2。
- 支持视频链接、BV 号及二者混合输入。
- 同批重复、当前用户已导入、当前用户正在导入的视频标记为 `SKIPPED`。
- 单项失败不影响其他任务，可仅重试失败项。
- 保留并展示当前用户最近 20 个批次。
- 服务重启后恢复未完成任务。
- 第一版不支持取消任务、UP 主主页导入或收藏夹导入。

## 数据模型

新增两张表：

- `video_import_batch`：批次归属用户、批次状态、各状态计数、创建和完成时间。
- `video_import_item`：所属批次、用户、标准化 BVID、原始输入、任务状态、失败原因、重试次数、关联视频及时间字段。

批次状态由明细汇总得到：存在排队或执行项时为 `RUNNING`；全部结束且至少一项失败时为 `PARTIAL_FAILED`；全部成功或跳过时为 `COMPLETED`。

明细状态限定为 `QUEUED`、`RUNNING`、`SUCCEEDED`、`SKIPPED`、`FAILED`。任务领取使用带旧状态条件的更新，确保同一明细只会被一个工作线程执行。

Cookie 仅作为执行导入所需的批次凭证使用，不出现在查询响应或日志中。数据库使用应用侧加密字段暂存；批次全部成功或跳过后立即清除。存在失败项时保留密文以支持“重试失败项”，重试完成后清除。

## 后端流程

1. 创建批次时校验登录用户、输入数量和格式，标准化 BVID 并在批次内去重。
2. 在同一事务中写入批次与明细；可提前判断的重复项直接写为 `SKIPPED`。
3. 提交事务后唤醒固定大小为 2 的后台执行器。
4. 执行器通过条件更新领取 `QUEUED` 明细，组装现有 `ImportVideoRequest` 并调用现有单视频导入服务。
5. 每项独立更新成功、跳过或失败状态，再刷新批次汇总。
6. 应用启动时将遗留 `RUNNING` 明细安全恢复为 `QUEUED`，重新调度。
7. 重试接口仅把当前用户指定批次内的 `FAILED` 明细重置为 `QUEUED`，不复制成功或跳过项。

为避免批量与单视频入口并发导入同一视频，视频创建仍依赖数据库唯一约束作为最终幂等防线；调度层的重复判断只用于更友好的状态展示。

## API 契约方向

实现前先在 `docs/API.md` 明确定义以下需要登录的接口：

- `POST /api/video-import-batches`：创建批次，接收多行输入列表和本次执行所需 Cookie，返回批次摘要。
- `GET /api/video-import-batches`：返回当前用户最近 20 个批次。
- `GET /api/video-import-batches/{id}`：返回批次及明细进度。
- `POST /api/video-import-batches/{id}/retry-failed`：重试当前用户批次中的失败项。

所有接口返回现有 `Result<T>` 结构。批次不存在或不属于当前用户时统一按资源不存在处理，避免泄露其他用户数据。

## 前端交互

在现有导入页面保留单视频入口，并增加批量模式：

- 多行文本框逐行接收视频链接或 BV 号，提交前展示有效数量和格式错误。
- 创建成功后进入批次进度视图，以低频轮询刷新状态。
- 展示总进度及每项的排队中、导入中、成功、已跳过、失败和失败原因。
- 失败批次提供“重试失败项”；终态后停止轮询。
- 页面刷新后可以从最近 20 个历史批次中恢复查看。

## 异常与安全

- 单项捕获可预期业务异常并保存适合用户查看的失败原因，未知异常保存通用提示，完整堆栈只记录服务端且不得包含 Cookie。
- 创建、查询、明细和重试均按当前用户过滤。
- 线程池队列有界，任务状态以数据库为准，内存通知丢失时由定时扫描补偿。
- 批次凭证不得返回前端、写入普通日志或长期保留。

## 验证

后端重点覆盖：输入规范化、50 项上限、批内去重、已导入跳过、并发领取、部分失败、仅重试失败项、重启恢复和跨用户拒绝。

前端至少执行生产构建，并手工验证混合输入、轮询终止、失败重试、刷新恢复和空历史状态。完整交付前运行后端 `mvn test` 与前端 `npm run build`。
