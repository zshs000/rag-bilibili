# 回答来源引用与时间戳跳转设计

## 目标

为助手消息增加可持久化的字幕来源。模型在正文中使用 `[1]`、`[2]` 编号引用，前端展示对应来源卡片；点击正文编号或卡片时，在新标签页打开 B站视频并跳转到字幕片段起点前 2.5 秒。刷新或重新进入历史会话后，引用仍然存在。

## 范围

- 单视频和全部视频会话均支持来源引用。
- 来源是生成回答时检索结果的快照，不依赖 `video`、`chunk` 或向量继续存在。
- 删除知识库视频后，仍然存在的历史消息保留来源快照；删除会话或消息时同步清理其来源。
- 不实现站内播放器、答案评测、检索重排或视频下载。

## 数据模型

新增 `message_source` 表，一条助手消息可关联多条来源：

- `message_id`：助手消息 ID。
- `citation_index`：回答中使用的编号。
- `vector_id`：产生来源的向量 ID，用于追踪。
- `bvid`、`video_title`：视频快照。
- `cid`、`page_number`：分 P 快照。
- `start_time_ms`、`end_time_ms`：字幕证据范围。
- `snippet`：检索时的字幕片段快照。
- `create_time`：创建时间。

`(message_id, citation_index)` 唯一。表不关联 `video` 外键，避免视频删除破坏历史来源；项目现有表也采用显式清理而非数据库外键，因此来源在会话/消息删除路径中显式删除。

## 后端流程

1. DashVector 按现有用户/视频过滤条件返回 TopK 文档。
2. 根据返回文档的向量 ID，批量关联 `vector_mapping` 和 `chunk`，得到可靠的视频标题、分 P、时间范围和字幕文本；该方式兼容已经导入的旧向量。
3. 上下文为每个候选来源编号，提示模型只用 `[n]` 引用提供的来源，禁止生成 URL。
4. 流式生成结束后，从完整回答中提取合法且去重的 `[n]`；不存在于候选集合中的编号被忽略。
5. 在同一事务中插入助手消息和实际引用的来源快照。
6. `end` SSE 事件返回助手消息 ID、完整回答和来源列表；历史消息 REST 响应返回同样的来源结构。

若模型没有输出合法引用，助手消息仍正常保存，`sources` 返回空数组，不把全部 TopK 冒充实际引用。

## API 与跳转链接

来源响应字段：

- `index`
- `bvid`
- `videoTitle`
- `pageNumber`
- `startTimeMs`
- `endTimeMs`
- `snippet`
- `jumpUrl`

后端生成：

```text
https://www.bilibili.com/video/{bvid}/?p={pageNumber}&t={max(0, startTimeMs - 2500) / 1000}
```

保留 0.5 秒精度；`pageNumber` 最小为 1。前端不接受模型生成的跳转地址。

这是向后兼容的响应扩展：旧消息返回 `sources: []`，现有 SSE 事件顺序 `start -> content* -> end` 不变，仅扩展 `end` payload。

## 前端交互

- `MarkdownContent` 根据结构化 `sources` 将匹配的 `[n]` 渲染为可信链接；无对应来源的编号保持普通文本。
- 助手消息下方按编号展示来源卡片，包含标题、P 数、`mm:ss–mm:ss` 和字幕摘要。
- 正文引用和卡片均使用 `target="_blank"`、`rel="noopener noreferrer"`。
- 流式完成时立即展示来源；重新加载后使用消息 REST 响应恢复。

## 一致性与安全

- 助手消息与来源快照事务写入，避免只有消息没有来源或反之。
- 历史消息查询先校验会话归属，再批量查询当前消息 ID 对应的来源，避免跨用户访问。
- 来源 URL 只由服务端结构化字段生成；前端继续使用 DOMPurify，不执行字幕内容中的 HTML。
- 删除会话前先删除对应来源，再删除消息。视频删除沿用现有会话删除语义；未被删除的全部视频会话消息，其来源快照不受视频删除影响。

## 验证

- URL 构造：2.5 秒提前量、零值钳制、多 P、小数秒。
- 引用解析：去重、顺序、非法编号、无引用。
- 消息事务：助手消息与实际引用来源一起写入。
- 历史查询：来源正确分组，旧消息为空数组，越权仍返回会话不存在。
- 删除路径：先清来源再清消息。
- SSE 序列化：`end.sources` 契约。
- 前端构建及手工检查正文链接、来源卡片和历史恢复。
